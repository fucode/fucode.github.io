01 • Fundamentals

What Is an API?

An Application Programming Interface (API) is a defined contract that allows one software system to communicate with another. In an enterprise, APIs help connect customer-facing applications, business services, databases, and third-party platforms.

01

Request

An application sends a request to an API endpoint. The request may include a URL, HTTP method, headers, authentication, and data.

Client → API
02

Business Logic

The receiving service validates the request, applies business rules, checks authorization, and retrieves or updates information in connected systems.

API → Services
03

Response

The API returns a response, often in JSON format. The response may contain requested data, a success status, or an error explaining what went wrong.

API → Client

A gateway can provide a centralized entry point for APIs. Typical responsibilities include routing, authentication integration, rate limiting, and monitoring.

API Service

The service handles business logic. It may validate input, retrieve data, call other services, or update enterprise records.

Security & Monitoring

Enterprise APIs commonly require authentication, authorization, encryption, audit logging, monitoring, and appropriate protection of sensitive data.

03 • API Communication

Common API Methods

HTTP methods describe the action a client wants to perform against an API resource.

Method Purpose Enterprise Example
GET Retrieve information. Retrieve a merchant's risk profile.
POST Create a resource or submit an operation. Create a new risk profile assessment.
PUT Replace a resource representation. Replace an entire resource when supported by the API.
PATCH Partially update a resource. Update a specific field on an existing record.
DELETE Delete a resource when permitted. Remove a resource under an authorized business process.

Request Components

  • Endpoint: The URL of the API resource.
  • Method: GET, POST, PUT, PATCH, or DELETE.
  • Headers: Metadata such as content type and authorization information.
  • Parameters: Values used to identify or filter resources.
  • Body: Data submitted with methods such as POST, PUT, or PATCH.

Response Components

  • Status code: Indicates the result of the request.
  • Response body: Data returned by the service, often JSON.
  • Headers: Additional response metadata.
  • Error details: Useful information for troubleshooting failed requests.
  • Correlation ID: A traceable identifier when provided by the enterprise platform.

05 • Delivery Lifecycle

How APIs Are Delivered in an Enterprise

API delivery typically involves business requirements, architecture, development, testing, security review, deployment, and ongoing monitoring.

1
Business Discovery

Identify the business problem, users, systems involved, data needed, and expected outcome.

2
API Requirements

Define endpoints, request fields, response fields, business rules, acceptance criteria, and error scenarios.

3
Architecture & Design

Determine service ownership, data flow, integration dependencies, security, and technical approach.

4
Development

Developers implement the API, business logic, data integration, validation, and error handling.

5
Testing & UAT

Validate functional behavior, integration scenarios, negative cases, data accuracy, and acceptance criteria.

6
Deployment & Monitoring

Release through approved environments and monitor availability, errors, performance, and operational health.

09 • Product Ownership

The Product Owner's Role in API Delivery

A Product Owner does not necessarily need to write the API. The PO is responsible for understanding the business value, defining requirements, prioritizing work, and helping the team deliver the right behavior.

01
Business Requirements

Define what the API must accomplish for the business and who will use it.

  • Business rules
  • Data requirements
  • Expected outcomes
02
User Stories & Acceptance Criteria

Translate requirements into actionable delivery work for the development team.

  • Endpoint behavior
  • Request and response fields
  • Positive and negative scenarios
03
Stakeholder Collaboration

Coordinate with architecture, engineering, security, data, operations, and business teams.

  • Dependencies
  • Prioritization
  • Delivery alignment
04
Testing & Validation

Confirm that the API behavior supports the business process and meets acceptance criteria.

  • UAT scenarios
  • Error handling
  • Data validation
05
Risk & Compliance

Ensure the requirements account for applicable security, privacy, audit, and regulatory needs.

  • Access control
  • Sensitive data
  • Auditability
06
Backlog & Delivery

Prioritize API-related work based on business value, dependencies, risk, and delivery capacity.

  • Backlog refinement
  • Sprint planning
  • Release readiness
10 • Quality Assurance

API Testing & Validation

API testing verifies that services behave as expected when they receive valid requests, invalid requests, missing data, and unexpected conditions.

From a PO perspective, testing helps ensure that the technical implementation supports the intended business process.

API Test Scenarios

  • Positive test: A valid request returns the expected data.
  • Negative test: Invalid input returns an appropriate error.
  • Authorization test: Unauthorized access is rejected.
  • Data validation: Required fields, formats, and business rules are enforced.
  • Integration test: Connected systems exchange the expected information.
  • UAT: The end-to-end business process meets acceptance criteria.
